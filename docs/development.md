# Development

For working on prblm-mailer itself.

## Setup

```bash
git clone https://github.com/prblmcodes/prblm-mailer.git
cd prblm-mailer
python -m venv .venv && source .venv/bin/activate
pip install -e ".[test]"
```

## Running the tests

```bash
DJANGO_SETTINGS_MODULE=tests.settings PYTHONPATH=. python -m django test tests
# or: pytest
```

The suite uses its own minimal settings (`tests/settings.py`) and a throwaway app
(`tests/testapp`) that exercises the form-page base classes. Nothing outside the repo is needed.

### Test across the supported range

The supported Wagtail and Django versions differ in admin internals and in the mail API often
enough that a green run on one proves little about another. Before trusting a change, run the
suite on **both ends** of the range. [uv](https://docs.astral.sh/uv/) builds each environment
in seconds:

```bash
# oldest
uv venv -p 3.12 /tmp/pm-old
uv pip install -p /tmp/pm-old/bin/python -e . "wagtail>=6.0,<6.1" "Django>=5.0,<5.1"

# newest
uv venv -p 3.12 /tmp/pm-new
uv pip install -p /tmp/pm-new/bin/python -e . "wagtail>=8.1,<9" "Django>=6.1,<6.2" "django-newsletter>=1.3,<1.4"

for v in old new; do
  DJANGO_SETTINGS_MODULE=tests.settings PYTHONPATH=. /tmp/pm-$v/bin/python -m django test tests
done
```

Wagtail 7 with Django 5.2 is a useful middle. Tests that only apply to Django 6.1 skip
themselves on older versions. The release workflow runs all three automatically.

### Cross-version rules

- **Generate StreamField migrations on the lowest supported Wagtail.** Newer Wagtail writes a
  format older versions can't load; the older format loads everywhere.
- The test app's migration depends on `('wagtailcore', '__first__')`; a pinned migration name
  breaks other Wagtail versions.
- On Wagtail 6, `RichTextBlock` values in fixtures must be `RichText(...)` objects, and
  `ListBlock` fixtures must go through `block.to_python(...)`.

## Project layout

| Module | Responsibility |
|---|---|
| `conf.py` | `PRBLM_MAILER` defaults and `get_setting()` |
| `models.py` | `Broadcast` (a newsletter), `SubscriberTag` (groups), `Subscriber` (read-only proxy), `EmailEvent`, `EngagementEvent` |
| `blocks.py`, `social.py` | The email blocks and the social platform list |
| `sending.py` | Rendering (MJML → HTML via mrml) and the four delivery modes |
| `subscriptions.py` | `subscribe_from_form` and the double opt-in |
| `segments.py`, `audience.py` | Groups, and who a newsletter goes to |
| `form_pages.py` | Base classes for Wagtail form pages |
| `signals.py` | Mailgun webhook handling: bounces, complaints, opens, clicks |
| `csv_io.py` | CSV import/export, shared by the admin and the commands |
| `checks.py` | Startup checks |
| `admin_views.py`, `wagtail_hooks.py` | The admin: Send page, confirm, duplicate, import/export |
| `views.py`, `urls.py`, `urls_bundle.py` | Public one-click unsubscribe and deny views; URL wiring |

The package must never import a host project's code; everything site-specific comes from
settings.

## Social icons

The social icons are PNGs in `prblm_mailer/static/prblm_mailer/icons/`, generated by
`scripts/build_icons.py` (needs `cairosvg`; the package itself never does). The script checks
its artwork against the platform list in `social.py` and refuses to run if they disagree.
Artwork is from Simple Icons (CC0), except LinkedIn (Font Awesome) and the email and website
marks.

## Releasing

1. Bump `version` in `pyproject.toml` and add the release to `CHANGELOG.md`.
2. Commit. The commit message becomes the GitHub Release notes, so make it a readable summary.
3. Tag and push:

   ```bash
   git tag -a v0.7.0b1 -m "prblm-mailer 0.7.0b1"
   git push origin main v0.7.0b1
   ```

`.github/workflows/release.yml` then runs the tests on all three version pairs, checks the tag
matches `pyproject.toml`, builds the wheel (failing if templates or static files are missing),
and publishes the GitHub Release with the wheel and source archive attached. Versions with
`a`, `b` or `rc` are marked as pre-releases.
